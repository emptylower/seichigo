Anitabi 同步链路失效
诊断报告与恢复方案

管理员面板的作品／图片同步已停摆两个月。根因有四个，彼此独立，其中一个足以让整条链路在第一个请求就死掉。

结论：代码没有被改坏，是上游 anitabi.cn 收紧了。同步管线当初建立在 3 个未公开接口 + 3 个主域抓取之上，而官方文档明文写着「请勿在任何场景下请求主域」。上游关闭这些入口后，管线没有任何可用的降级路径。
诊断日期 2026-08-09 最后一次同步 2026-06-08 最后一次成功 从未 受影响图片 14,893 条死链

四个根因

F1

上游 www.anitabi.cn 已从 DNS 中移除阻断

Google 与 Cloudflare 两家 DoH 解析器一致返回 NXDOMAIN（权威 SOA 否定应答），同域下 w / api / image / cdn / navi 均正常。上游把站点迁到了 w.anitabi.cn，但自己的 apex 还挂着一条 301 → www 的死链。

# 两家解析器交叉验证 dns.google www.anitabi.cn Status=3 NXDOMAIN w.anitabi.cn Status=0 cloudflare-dns www.anitabi.cn Status=3 NXDOMAIN w.anitabi.cn Status=0 # 本机 dig 不可信：Clash TUN fake-IP 全部劫持为 198.18.x.x

而 lib/anitabi/api.ts:35 的默认 siteBase 自首个提交 b20ad05 起就是这个域名，从未改动。生产库给出了精确的死亡时间：

AnitabiSourceCursorlastSuccessAt来源
bangumi2026-06-08apiBase
usersJson2026-02-15siteBase/d/users.json
changelog2026-02-15siteBase/CHANGELOG.md
iconsSvg2026-02-15siteBase/api/bangumi/icons.svg

更要命的是 resolveAnitabiAssetUrl()（utils.ts:123）会把相对路径拼到 siteBase 上再落库，于是死域名被写进了数据：

AnitabiPoint.image 的 host条数状态
image.anitabi.cn26,934域名存活，但被 WAF 拦（见 F2）
www.anitabi.cn14,893host 已死，但路径完好（见 F5）

更正：这 14,893 条并非「永久死链」。imageProxy.ts:179 与 r2Mirror.ts:68 在读取／镜像时会调用 normalizeAnitabiMirrorUrl()，把 www.anitabi.cn/images/X 改写成 image.anitabi.cn/X。所以它们不是死于 DNS，而是和另外 26,934 条一样死于 F2 的 WAF —— 这意味着修法比原先判断的简单得多，见 F5。

F2

整个 anitabi.cn 域启用了 Cloudflare WAF 拦截阻断

返回 4546 字节的 Attention Required! | Cloudflare — Sorry, you have been blocked 页面。换 UA、补齐 Referer／Origin／Accept-Language 全套浏览器头都无效，因此不是 UA 规则，而是按来源 IP／ASN 或 bot score 判定。

关键在于区分两类端点 —— 这决定了恢复方案的形状：

端点官方文档收录首次接触结果
/bangumi （全量列表）否403 · 自始至终
/bangumi/{id}否403 · 自始至终
/bangumi/{id}/points否403 · 自始至终
/bangumi/{id}/lite是可用，随后被限流
/bangumi/{id}/points/detail是200 OK，随后被限流

三个观测点的对照说明了封锁的形状：

日本 KDDI 住宅 IP（Clash 出口） 全部 403 中国安徽移动 住宅 IP（DIRECT） /points/detail 200 → 约 30 次请求后转 403 Anthropic 机房 IP（仅 4 次请求） 全程 403 ← 未被限流，仍然被拦 对照 example.com 200

推论：境外／机房出口被整体拦截；中国境内住宅 IP 可用但有相当激进的速率限制。需要坦白一点：我今天的排查本身触发了限流，把中国 IP 也打进了惩罚区，所以后期的 403 有一部分是我造成的，需要冷却后复测。

F3

定时任务在 Cloudflare 迁移时遗失高

Cron 定义还留在 vercel.json，而线上部署的是 wrangler.jsonc，其中完全没有 triggers.crons。只有独立的图片镜像 worker 还带着 cron。所以即便上游可达，也没有任何东西会去触发同步 —— 这独立解释了「2026-06-08 之后一条同步记录都没有」。

vercel.json crons: /api/cron/anitabi/daily "10 3 * * *" ← 不再生效 wrangler.jsonc （无 triggers 字段） ← 实际部署 workers/anitabi-mirror/wrangler.jsonc crons: */5 * * * * ← 仅图片镜像
F4

同步从未记录过一次成功中

AnitabiSyncRun 中所有模式的 last_success 均为 null，只有 partial 和 failed。最后一次 delta 死于 Prisma 事务超时（限 5000ms，实耗 5580ms），与上游无关。前三项修好后，这个仍会挡路。

本地复现

已搭好一套完全隔离的本地环境，不碰生产库、不碰真实上游，可以反复迭代：

组件位置说明
Dev serverlocalhost:3100Next.js 15.5.15，已就绪
沙箱数据库postgresql://localhost:5432/seichigo_synclab由本地 seichigo 克隆，7,933 作品 / 30,845 点位
Mock 上游scripts/anitabi-mock-upstream.mjs只实现官方文档收录的两个端点，其余一律 403
同步 harnessscripts/anitabi-sync-lab.mts跑真实 runAnitabiSync()；DATABASE_URL 非本地则拒绝启动

跑起来的结果精确复现了生产故障 —— 整条同步只发出了一个上游请求就结束了：

$ npx tsx scripts/anitabi-sync-lab.mts delta { "status": "failed", "scanned": 0, "changed": 0, "message": "Request failed 403 http://127.0.0.1:4555/bangumi" } mock 上游收到的全部请求： 403 /bangumi BLOCKED (not part of the official API)

此外 source/client.ts:48 对 4xx（429 除外）直接抛错不重试，所以 /bangumi 在 408ms 就让整个 run 失败；而三个 siteBase 请求属于网络错误，会走满 4 次重试（1+3+8 秒），每个耗掉约 14 秒 —— 已经超过 ANITABI_SYNC_MAX_RUNTIME_MS 默认 20 秒预算的大半。

官方 API 能否撑起现有数据模型

官方文档（anitabi/anitabi.cn-document/api.md）只收录两个数据端点。把它们与现有 schema 逐字段比对后，结论是大部分可覆盖，但有明确缺口：

字段原来源官方 API 是否提供补救
id, cn, title, city, cover, color, modified/bangumi/lite 提供直接替换
geo, zoom/bangumi/lite 提供代码里 RawLite 类型漏声明了，补上即可
cat, description, tags/bangumi不提供改用 Bangumi 官方 API api.bgm.tv/v0/subjects/{id}
点位 name/cn/geo/ep/s/image/origin/originURL/points/detail提供本来就是官方端点
density, mark, folder, uid, reviewUid/points（摘要）不提供库中填充率 33–96%，且代码有引用；upsert 时必须保留旧值，不能覆盖为 null

真正的硬缺口是「枚举」：官方 API 没有任何列出全部作品的入口。现有 delta 逻辑完全依赖 GET /bangumi 返回的全量数组＋modified 时间戳做变更检测，这个设计无法直接移植。

F5 · 突破口：上游有第二套 CDN，且没有同样的封锁

从上游官方客户端仓库（anitabi/anitabi-trace）的源码里翻到一个文档里从未提及的 host：img-tc.anitabi.cn。它的 CNAME 指向 eo.dnse3.com —— 腾讯云 EdgeOne，与 README 中「CDN 和安全防护由 Tencent EdgeOne 赞助」正好对上。整个域的 CDN 归属是这样分裂的：

同一出口 IP、同一路径的 A/B 对照，差别完全来自 CDN 而不是 IP：

GET /points/272510/39zlm4tj.jpg?plan=h160 image.anitabi.cn 403 text/html 4546 B ← Cloudflare 拦截页 img-tc.anitabi.cn 200 image/jpeg 11341 B ← eo-cache-status: HIT 再用库里真实的一条 www 记录验证（user 上传家族）： raw www.anitabi.cn/images/user/1181/bangumi/1851/points/n7zx3k2ft-1723655509302.jpg → image.anitabi.cn/user/1181/... 403 → img-tc.anitabi.cn/user/1181/... 200 image/jpeg 7430 B

结论：图片同步有现成的解，且不需要任何对外沟通。img-tc.anitabi.cn 与 image.anitabi.cn 路径结构完全一致，两个 URL 家族（/points/{bid}/{pid}.jpg 规范族 与 /user/{uid}/bangumi/{bid}/points/{pid}-{ts}.jpg 用户上传族）都能取到，?plan= 参数同样生效。改一个 host 即可让全部 41,827 条点位图 + 封面恢复。

点位同步则没这么好运：我按 api-tc / api-eo / data-tc 等十余个可能的命名做了 DNS 扫描，不存在 EdgeOne 版的 API host。api.anitabi.cn 只有 Cloudflare 一条路，仍然被拦。

官方客户端印证的 API 现状

把 org 下五个客户端仓库（Swift app / anitabi-trace / seichi-grader / junrei-level / image-merge）全部 clone 后，提取其中所有 anitabi.cn 调用，得到的端点集合与文档完全一致，没有任何隐藏接口：

api.anitabi.cn/bangumi/{id}/points/detail ← 点位数据，唯一的数据端点 image.anitabi.cn/bangumi/{id}.jpg?plan=h360 ← 封面（规范形式） image.anitabi.cn/points/{bid}/{pid}.jpg?plan=h160 ← 点位图（规范形式） img-tc.anitabi.cn/bangumi/{id} ← EdgeOne 镜像，仅出现在 anitabi-trace

另外几点值得记录：api.md 的实质内容自 2024-02-21 起未再改动（今天那批提交只是 README 加社交徽章），所以「官方只有两个端点」是稳定事实而非临时状态；navi.anitabi.cn 仓库里只有 Docusaurus 模板文章，没有额外 API 文档。

还有一个反向证据：Swift 客户端 WebViewStore.swift:129 至今仍然打开 https://www.anitabi.cn/map。既然这个域名已经 NXDOMAIN，官方 App 现在自己也是坏的 —— 这更像是一次仍在进行中的上游事故或迁移疏漏，而不是有计划的下线。这提高了「反馈给维护者后会被修复」的可能性。

恢复方案

先说前提：方案取决于一个还没验证的事实 —— Cloudflare Workers 的出口能否穿过 anitabi 的 WAF。我的两个观测点都是机房／代理 IP 且都被拦，Workers 出口同样是机房 IP，大概率也被拦；但 Cloudflare→Cloudflare 的子请求路径有其特殊性，不实测不能下定论。这是第一步要做的事。

文档中邀请联系维护者申请权限，拦截页也明确写了 email the site owner。说明用途、申请白名单或 API key，顺带确认 www 下线与推荐的新基址。

建议执行顺序

第 0 步

停止一切对上游的自动请求，等待冷却

当前 IP 仍在 WAF 惩罚区。在确认策略之前不要再跑任何批量抓取，否则会把仅存的可用出口也打掉。

第 1 步

实测 Workers 出口是否被拦

部署一个只做单次 fetch('https://api.anitabi.cn/bangumi/115908/lite') 的最小 worker，打印状态码。这一个数字决定后面走 A、B 还是 D。

第 2 步

图片链路：切到 img-tc.anitabi.cn（可立即做，不依赖任何外部条件）

  • 在 imageNormalize.ts 的 normalizeAnitabiMirrorUrl() 里，把重写目标由 image.anitabi.cn 改为 img-tc.anitabi.cn；因为 computeCanonicalImageUrl() 与 imageProxy 都走这个函数，一处改动即可覆盖显示、代理、R2 镜像三条路径。
  • 建议做成可切换的 host 列表而非硬编码，让 EdgeOne 与 Cloudflare 互为兜底 —— 上游修好 Cloudflare 侧之后不必再改代码。
  • 注意 computeMirrorKey() 把 hostname 编进了 R2 key（mirror/v1/{hostname}/{hash}），换 host 会导致全部已镜像对象 key 失效。要么在 key 里对这两个 host 做归一化，要么接受一次全量回填。这是改动前必须先决定的一点。
  • 库里那 14,893 条 www 记录不需要迁移 —— 重写函数已经处理，路径本身是完好的。
第 3 步

点位链路：联系上游取得正式访问（方案 A）

这一条没有技术捷径：api.anitabi.cn 只有 Cloudflare 一条路且不存在 EdgeOne 版本。发邮件说明用途、承诺频率、申请白名单或 API key。顺带告诉他们 www.anitabi.cn 和 cdn.anitabi.cn 已 NXDOMAIN、官方 App 因此打不开地图 —— 这是对双方都有价值的信息，也是一个自然的沟通切入点。

第 4 步

把 cron 迁进 wrangler.jsonc

否则一切修好之后仍然不会自动运行。同时删掉 vercel.json 里已失效的定义，避免下一个人再被误导。

第 5 步

按方案 C 改造同步管线

  • 枚举层换成库内 ID 轮转；modified 比对改由 /lite 提供。
  • 只保留 /lite 与 /points/detail，彻底移除三个主域抓取。
  • upsert 时对 density/mark/folder/uid/reviewUid 采用「有新值才写」，避免把已有数据抹成 null。
  • 加全局限速与退避；4xx 不重试的现有行为要保留，但 403 应记入 run 报告而不是静默失败。
第 6 步

修 F4 的事务超时，并补上监控

拆掉 5 秒事务或调大上限。加一个上游健康探针，两个 CDN 分别探 —— 这次故障从 2 月潜伏到 8 月才被发现，缺的就是这个。

需要你判断的两件事

1 · 数据许可

官方文档声明地标数据以 CC BY-NC-SA 4.0（署名／非商业性使用／相同方式共享）共享，并要求在展示截图旁标注 origin 文字并实现 originURL 跳转。如果 seichigo 有商业化计划，镜像这份数据需要先想清楚；这也直接影响申请白名单时怎么描述用途。

2 · 我没能验证的部分

  • Workers 出口是否被拦 —— 只能实测，见第 1 步。
  • 官方两个端点在冷却后的真实可用性与速率上限 —— 我的探测污染了样本，需要隔一段时间用单个请求复测。
  • www 下线是否有官方公告 —— 仓库内 changelog 停更在 2024-07，线上 navi.anitabi.cn 同样被 WAF 拦住，没读到。
