## 任务 1：CUT-3 —— 阶段推断改用轻量投影

`lib/planAgent/loop.ts:280` 今天为了推断阶段拉整棵 `getPlan(PLAN_INCLUDE)`——**实测 5 条串行 SQL、23.2 KB**，其中第 4、5 条完全是为了 `item.point`（含 `i18n where language='en' take 1`）。而 `derivePlanStage` **根本不读 `item.point`**。

### 新增领域类型与仓储方法（`repo.ts` / `repoPrisma.ts` / `repoMemory.ts`）

```ts
export type TripPlanStageInputs = {
  bangumiIds: number[]
  startDate: Date | null
  dayCount: number
  /** 是否存在任一 items[].pointId 为真值（非 null 且非空串）的条目 */
  hasPointItem: boolean
}

getStageInputs(planId: string): Promise<TripPlanStageInputs | null>
```

Prisma 实现（**已用开发库实测：连 `notIn` 一起仍只发 1 条 SQL**，EXISTS 子查询）：

```ts
const row = await prisma.tripPlan.findUnique({
  where: { id: planId },
  select: {
    bangumiIds: true,
    startDate: true,
    dayCount: true,
    _count: { select: { days: { where: { items: { some: { pointId: { not: null, notIn: [''] } } } } } } },
  },
})
if (!row) return null
return { bangumiIds: row.bangumiIds, startDate: row.startDate, dayCount: row.dayCount, hasPointItem: row._count.days > 0 }
```

`repoMemory.ts` **必须用与 `stageInputsOfPlan` 逐字相同的 JS 谓词**：
```ts
hasPointItem: plan.days.some((day) => day.items.some((item) => item.pointId))
```

### 改 `lib/planAgent/stage.ts`

```ts
export function derivePlanStage(input: {
  plan: TripPlanStageInputs          // ← 由 TripPlanWithDays 改为此
  messages: TripPlanMessage[]
  quality: PlanQualityReport | null
}): PlanStage {
  const { plan, messages, quality } = input
  if (!plan.bangumiIds.length) return 'works'
  if (!plan.startDate || plan.dayCount <= 1) return 'dates'
  if (!plan.hasPointItem) return 'points'          // ← 原来的两行合并
  if (quality && !quality.passed) return 'enrich'
  // 以下（lastDaymapIndex / humanAfterDaymap / deliver / revise）一行不动
}

/** 持有完整 plan 的调用方（测试等）用它构造 stage 输入 */
export function stageInputsOfPlan(plan: TripPlanWithDays): TripPlanStageInputs {
  return {
    bangumiIds: plan.bangumiIds,
    startDate: plan.startDate,
    dayCount: plan.dayCount,
    hasPointItem: plan.days.some((day) => day.items.some((item) => item.pointId)),
  }
}
```

`loop.ts:280` 的 `deps.repo.getPlan(...)` 换成 `deps.repo.getStageInputs(...)`，守卫与后续三行不变（`updateStage` 那段见 CUT-6）。

### ⚠️ 硬性约束

- **必须用带 `where` 的过滤型 relation count**，不得用裸 `_count: { days: true }`。裸计数只回答"有几天"——一个有 3 天、条目全是外部地点（`pointId=null`）的计划会被从 `points` 误判成 `enrich`/`deliver`。`tests/planAgent/stage.test.ts` 里有现成用例覆盖这一格。
- **必须写 `{ not: null, notIn: [''] }`**，不许写裸 `{ not: null }`。JS 侧 `item.pointId` 的真值判断是"非 null 且非空串"，少了 `notIn` 就会让 `pointId=''` 这一格判错。
- **`derivePlanStage` 的参数类型必须是显式的 `TripPlanStageInputs`（带 `hasPointItem: boolean`），不许"结构性放宽类型"**（例如 `Pick<TripPlan,...> & { days: Array<{ items: ... }> }`）。放宽能让测试一行不改，但它把"轻量投影必须自带点位存在性谓词"这个契约藏起来了——将来有人传一棵被截断的 days 树进来，类型检查照过、stage 静默变错。
- `getPlan` **保留不动**，新方法是并存不是替换。
- `loop.ts:280` 附近那段中文注释的意思要保留（"从持久化证据推断当前阶段"），按新代码调措辞即可。

### 等价性要点（写进注释/PR，不要自行推翻）

- `derivePlanStage` 对 `plan` 的**全部**读取只有：`bangumiIds.length`、`startDate`、`dayCount`、`days.length`、`days[].items[].pointId` 的真值。不读 `stage`/`title`/`status`/`userId`/`preferences`/`updatedAt`，不读 day 的任何列，**更不读 `item.point`**。
- `!plan.days.length || !hasPointItem ≡ !hasPointItem`：`[].some()` 恒 false，四格真值表两式取值完全相同。所以合并成一行是等价的。
- `quality` 来自最后一条 daymap 消息（`listMessages` 产出），与 `getPlan` 无关。
- `buildStageContext` 只读 `(stage, quality)`，两者都已证明不变。
- loop 里的 `deps.repo` 被 `withModelUsageInRunLog` 与 `withFencing` 两层 Proxy 包过，**两者都是透明转发**，新增仓储方法穿得过去，两处都不用改。

## 任务 2：CUT-6 —— `updateStage` 的**发起时刻**推到首次模型请求发出之后，并加栅栏

`loop.ts` 今天在阶段推断之后立刻 `await deps.repo.updateStage(...)`，注释自己写着"阶段缓存写失败不影响本轮对话"，却仍然阻塞在关键路径上，白占一次往返。

### 新增带栅栏的写（`repo.ts` / `repoPrisma.ts` / `repoMemory.ts`）

```ts
updateStageIfActive(planId: string, token: string, stage: string): Promise<void>
// Prisma：await prisma.tripPlan.updateMany({ where: { id: planId, agentRunToken: token }, data: { stage } })
```

### 改 `loop.ts`

前奏块把 `await updateStage` 换成记一个待写值：
```ts
let pendingStageWrite: PlanStage | null = null
// ...推断完成后
pendingStageWrite = stage
```

在**首次模型请求发出处**释放（现有代码里 `runTiming?.markModelRequestSent()` 与 `deps.createMessage(...)` 相邻的那一处）：

```ts
runTiming?.markModelRequestSent()
const modelCall = deps.createMessage({ ... }, onDelta)
afterModelRequestIssued()          // ← 拿到 promise 之后、await 之前
response = await modelCall
```

```ts
// 放在 loop 顶层闭包里
const afterModelRequestIssued = () => {
  const s = pendingStageWrite
  pendingStageWrite = null
  if (!s) return
  const write = deps.runToken
    ? () => deps.repo.updateStageIfActive(deps.planId, deps.runToken!, s)
    : () => deps.repo.updateStage(deps.planId, s)     // 无 token（单测/旧调用）走今天的无栅栏写
  ;(deps.runInBackground ?? runInBackground)(() => write().catch(() => undefined))
}
```

### ⚠️ 硬性约束

- ⚠️ **派发点必须在 `deps.createMessage(...)` 被调用之后（拿到 promise、`await` 之前），不是在它 resolve 之后。** 挂在 resolve 之后会导致首次模型调用抛错（网络错误 / `RunFencedError` / abort）时**完全不写** stage——而今天是无条件写。那是新增的丢弃路径，不是原注释所说的"写失败可忽略"。
- ⚠️ **必须加 `updateStageIfActive` 栅栏，不许沿用无栅栏的 `updateStage`。** 今天 `updateStage` 的 where 只有 id，但它执行的时刻我们必然持有 token，所以"持有"在那一刻恒真。写推后之后恒真不再成立：run A 算出 `stage='enrich'` → 用户停止 → 用户再发一条 → run B 写下 `stage='revise'` → run A 的延后写把它覆写回 `'enrich'`，触发一次凭空的 `plan_updated` + 客户端全量 refetch，且 stage 缓存一直错到下一次 run。
- ⚠️ **内层 `.catch(() => undefined)` 必须保留**：今天的失败是静默吞掉；`runInBackground` 自己会 `console.warn`，加了 catch 才保持原样。
- ⚠️ **`pool=1` 下光去掉 `await` 是没用的**——未 await 的写只要在模型请求之前被**发起**，就会 FIFO 占住那条唯一连接。所以落点必须在模型请求确实发出之后。
- ⚠️ **不要顺手砍掉首轮的 `renewLease`**（在 `createMessage` 前面几行）。它不只是续租，还是首次模型调用前唯一的栅栏：今天用户在前奏期间点停止，这一轮**不会发出任何模型请求**。砍掉就变成"模型请求已发出再中止"，多烧一次调用、可能已流出 reasoning。
- ⚠️ **不要顺手删掉 loop 入口的 `isAgentRunStopped`**（那是另一条并发防线，已被评审明确否决）。
- 已知取舍（写进注释）：run 在首个模型回合前被硬杀 → 这一轮不写 stage。这正是今天注释接受的，下一轮 run 会重新推断并回写。
