## 背景：为什么这三读可以省

内部路由今天在启动路径上调 `getBillingService().getAccount(owner.userId)`——那是
**3 条串行 SQL**（`users.get` + `ledger.hasEntries` + `ledger.balance`）——但它对结果
的**全部消费只有两个字段**：

```ts
{ entitlements: billingAccount.entitlements, runCapMicros: billingAccount.runCapMicros }
```

而这两个都是 `tier` 的**纯查表函数**：`TIER_ENTITLEMENTS[tier]`（`Record<Tier, Entitlements>` 常量表）
与 `runCapMicros(tier)`（同样是 tier 索引的常量表）。`isAdmin` 不参与（它只影响
`canStartRun`/`reserveRun`，那是 POST 侧的事）。`hasEntries` + `balance` 那两条 SQL 的
唯一产出是 `balanceMicros`/`remainingPercent`/`budgetMicros`——**内部路由一个都不用**。

所以：**只要把 POST 时刻已经拿到的 tier 随队列消息带过来，这三条 SQL 就全是白跑的。**

`getAccount` 的三个写分支（F2 降档、周期滚动、首次 grant）在 POST 侧同一次用户操作
里**已经无条件执行过**（POST 开头的 `Promise.all` 早于所有提前返回），且各自的条件
在执行后都翻假。所以今天内部路由的这次 `getAccount` 在任何可达路径上都是**纯读**。

这也不是引入新的陈旧性：**内联 SSE 路径今天就已经用 POST 时刻的能力表**，本刀只是
把队列路径拉齐到内联路径。

## 任务 1：队列消息加可选 `tier`

`lib/planAgent/queueMessage.ts` 有**零 import 纪律**（worker 入口要引用它，不能把
Prisma/Next 打包进去）。所以像既有的 `QueueSupportedLocale` 一样，**就地重复字面量
联合并加同步注释**，不要 import `Tier`：

```ts
/**
 * 与 lib/billing/tiers 的 Tier 同构的字面量联合：为满足"零 import"约束
 * 在此重复声明；两处口径变更时必须同步（free/standard/pro）。
 */
type QueueTier = 'free' | 'standard' | 'pro'

export type PlanAgentQueueMessage = {
  // ...既有字段一个不动
  /**
   * 授权本次 run 的档位快照——POST 时刻 getAccount 得到的**有效 tier**
   * （已含 F2 降档），**不是消费时刻的档位**。缺失或无法识别时，消费者
   * 必须回落到 getAccount 三读，绝不能回落 free。
   */
  tier?: QueueTier
}
```

### ⚠️ 硬性约束

- ⚠️ **`isPlanAgentQueueMessage` 不得对 `tier` 做任何"不认识就拒"的校验。** 允许的最强写法是 `msg.tier === undefined || typeof msg.tier === 'string'`；**推荐完全不校验**（未知字段本来就被忽略）。
- 为什么：校验器返回 `false` → 内部路由 400 → 消费者 `console.error` 后**无条件 `ack()`**（队列配的是 `max_retries: 0`）→ **消息被彻底销毁**。此时 human 消息已落库、busy 锁占着 90 秒，用户这一轮只能靠 TTL 过期 + `interrupted→resume` 找回，而 POST 已 `reserveRun` 的预扣要等 16 分钟的孤儿清扫才退。将来加第 4 档（如 `'team'`）时，滚动窗口内就会触发这条。
- `v` 保持 `1`，不要升版本。

## 任务 3：内部路由消费 tier

```ts
const QUEUE_TIERS = new Set(['free', 'standard', 'pro'])
const TIER_PASSTHROUGH_MAX_AGE_MS = 120_000

const enqueuedAge = Date.now() - Date.parse(body.enqueuedAt)
const passthroughTier =
  process.env.PLAN_AGENT_TIER_PASSTHROUGH !== '0' &&
  typeof body.tier === 'string' &&
  QUEUE_TIERS.has(body.tier) &&
  Number.isFinite(enqueuedAge) &&
  enqueuedAge >= 0 &&
  enqueuedAge <= TIER_PASSTHROUGH_MAX_AGE_MS
    ? (body.tier as Tier)
    : null

const billing = passthroughTier
  ? { entitlements: TIER_ENTITLEMENTS[passthroughTier], runCapMicros: runCapMicros(passthroughTier) }
  : /* 今天的 getAccount 三读 + free 兜底，逐字不变 */
```

### ⚠️ 硬性约束

- ⚠️ **`TIER_PASSTHROUGH_MAX_AGE_MS` 必须实现，不许省。** 陈旧性窗口**不是**队列的几秒延迟：内部路由对 `body.enqueuedAt` 今天没有任何年龄检查，队列配的是 `max_concurrency=10`、`max_batch_size=1`，超过 10 个计划并发时消息会在队列里排**分钟级**。真实上界是队列深度，不是投递延迟。
- ⚠️ **缺失 / 不认识 / 超龄 / 开关为 `'0'` → 一律回落 `getAccount` 三读**（今天的代码逐字保留），**绝不回落 `TIER_ENTITLEMENTS.free`**。`free` 兜底只保留在今天原本的位置：**`getAccount` 抛错或返回 `null`**。这两处一定要分清楚。
- ⚠️ 开关 `PLAN_AGENT_TIER_PASSTHROUGH` **默认开**（即 `!== '0'` 才透传），置 `'0'` 是回滚手段。
- 保留今天 `getAccount` 那段的中文注释（"G3：getAccount 失败必须 fail-closed 回落免费档"），按新结构调措辞。

## 任务 4：测试

`tier` 取 `undefined` / `'team'`（未知）/ `null` / `123` / `'Pro'`（大小写不符）时，

### 内部路由（`tests/api/plan-agent-internal-run.test.ts` 或 `plan-agent-queue.test.ts`）
- `tier='pro'` 且 `enqueuedAt` 新鲜 → **`getAccount` 一次都不调**，且 `billing.entitlements` 与 `TIER_ENTITLEMENTS.pro` 逐字段相等、`runCapMicros` 与 `runCapMicros('pro')` 相等。

- `tier='team'`（不认识）→ 同上走 `getAccount`。
- `enqueuedAt` 超过 `TIER_PASSTHROUGH_MAX_AGE_MS` → 走 `getAccount`。
- `PLAN_AGENT_TIER_PASSTHROUGH='0'` → 走 `getAccount`。
- `getAccount` 抛错 → 回落 `free`（今天的行为，逐字保留，回归）。
