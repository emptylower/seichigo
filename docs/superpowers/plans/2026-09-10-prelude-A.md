## 任务 2：P0-B 实测两条 SQL 形态（用开发库，出证据）

在 `scratch/` 下写一个一次性脚本，连**开发库**（`.env` 的 `DATABASE_URL`），开 Prisma query 事件日志，打印下面两个查询实际发出的 SQL 原文与条数。

脚本写法（本仓库的 Prisma 是 driver-adapter 模式，裸 `new PrismaClient()` 会抛 P2038）：

```ts
import { PrismaClient } from '@seichigo/prisma-client-runtime'
import { PrismaPg } from '@prisma/adapter-pg'
const prisma = new PrismaClient({
  adapter: new PrismaPg({ connectionString: process.env.DATABASE_URL }),
  log: [{ emit: 'event', level: 'query' }],
})
prisma.$on('query', (e) => console.log('SQL:', e.query, '|params:', e.params))
```

要测的两条：

**(a)** `prisma.tripPlan.updateManyAndReturn({ where: { id, agentRunToken }, data: { agentBusyUntil: new Date(...) }, select: { userId: true } })`

要回答的**不是**条数，而是：**WHERE 子句里是否仍然带着 `agentRunToken`**。
- 若是单条 `UPDATE ... WHERE (id=$1 AND agentRunToken=$2) RETURNING ...` → 好，CUT-1 按 master 的写法做。
- 若被拆成 `SELECT ... WHERE id AND agentRunToken` + `UPDATE ... WHERE id IN (...)`，即第二条丢了 token → **降级方案**：CUT-1 改成 `renewAgentRun()` + `findUnique({ where: { id }, select: { userId: true } })` 两次调用（仍省 4 条），并在报告里写明。

**(b)** `prisma.tripPlan.findUnique({ where: { id }, select: { bangumiIds: true, startDate: true, dayCount: true, _count: { select: { days: { where: { items: { some: { pointId: { not: null, notIn: [''] } } } } } } } } })`

确认加上 `notIn: ['']` 之后**仍然只发 1 条 SQL**，把 SQL 原文抄进报告。
（这条是给下一批 CUT-3 用的**预先侦察**，本批**不要**真的实现 `getStageInputs`。）

同时顺手测一下作为对照：`getPlan(planId)`（即带 `PLAN_INCLUDE` 的那个）实际发出几条 SQL。

## 任务 3：CUT-8 —— `title.ts` 的 `getPlan` → 只取 title 的投影

`lib/planAgent/title.ts:29-30` 今天为了读一个 `title` 拉了整棵 `PLAN_INCLUDE`（days→items→point→i18n 四层嵌套，多条串行 SQL、20+ KB）。它跑在 `execute.ts` 的 `Promise.all` 另一支上，在 `pool=1` 下会和主 loop 抢唯一那条连接。

**新增仓储方法**（三处：`repo.ts` 接口、`repoPrisma.ts`、`repoMemory.ts`）：

```ts
getPlanTitle(planId: string): Promise<string | null>
```

Prisma 实现：
```ts
const row = await prisma.tripPlan.findUnique({ where: { id: planId }, select: { title: true } })
return row?.title ?? null
```

`title.ts` 改成：
```ts
const title0 = await deps.repo.getPlanTitle(deps.planId)
if (title0 === null || title0 !== DEFAULT_PLAN_TITLE) return
```

⚠️ 约束：
- **`getPlan` 保留不动**（别的调用点还在用）。新方法是**并存**，不是替换。
- `TripPlan.title` 在 schema 与领域类型里都是非空 `string`，所以 `null` 唯一对应"计划不存在"，与今天的 `!plan` 是同一判定。空串 `''` 会原样返回并被第二个条件挡掉——与今天一致，**不要**写成 `if (!title0)`。
- `updateMeta` 写入侧、"刻意不走 run-token 栅栏"、"失败静默吞掉"三条既有语义**一行不动**。

## 任务 4：CUT-1 —— 内部路由删掉 `getPlan`，存在性 + `userId` 折进续租

`app/api/internal/plan-agent/run/route.ts:96-107` 今天先 `getPlan`（多条串行 SQL、23 KB）再 `renewAgentRun`，而它对 `getPlan` 结果的**全部消费只有两处**：`if (!plan)` 和 `plan.userId`。`plan` 对象不会传进 `executePlanAgentRun`。

**新增仓储方法**（三处）：

```ts
/** 续租并返回计划归属用户。token 不符与计划不存在都返回 null（同一语义）。 */
renewAgentRunOwner(planId: string, token: string, ttlMs: number): Promise<{ userId: string } | null>
```

Prisma 实现（若 P0-B(a) 结论良好）：
```ts
const rows = await prisma.tripPlan.updateManyAndReturn({
  where: { id: planId, agentRunToken: token },
  data: { agentBusyUntil: new Date(Date.now() + ttlMs) },
  select: { userId: true },
})
return rows[0] ?? null
```

`repoMemory.ts` 用与既有 `renewAgentRun` **逐字相同**的 where/data 语义实现：命中才写 `agentBusyUntil` 并返回 `{ userId: plan.userId }`，否则返回 `null` 且不写。

路由改成：
```ts
const deps = await getTripPlanApiDeps()
const owner = await deps.repo.renewAgentRunOwner(body.planId, body.runToken, AGENT_BUSY_TTL_MS)
if (!owner) {
  return NextResponse.json({ skipped: 'stale_token' })
}
// 后续原本 plan.userId 的地方改用 owner.userId
```

⚠️ 约束：
- **原 `renewAgentRun` 保留不动**——`lib/planAgent/execute.ts:63` 的 `renewLease` 还在用它，**那个文件本批不许改**。
- 今天"计划不存在"与"token 不符"两个分支返回的是**同一个表达式 `NextResponse.json({ skipped: 'stale_token' })`、同一个默认 200 状态码**。改后两种情况都由 `updateMany` 匹配 0 行统一产生 `null`，**响应必须逐字节不变**。
- 保留 `:96` 那段中文注释的意思（"被停止/被接管/已结束都会在这里失败——直接跳过，绝不重复执行同一回合"），按新代码调整措辞即可。
- `getAccount` 那段（`:109-119` 的计费装配 + free 兜底）**本批一行不动**，只是 `plan.userId` 换成 `owner.userId`。
